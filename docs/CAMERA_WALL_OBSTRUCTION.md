# Native JX3 camera wall obstruction

Reverse-engineered from the installed client engine on 2026-09-23. This adds a
new research note; existing camera research files were not changed.

## Result

The native third-person chase camera has a real scene-collision obstruction
path. It is controlled by engine `[Camera]` setting `bObstructdAvert`; the
compiled default is **enabled**. On a camera update, the chase camera tests
several line segments between the desired camera position and the look-at
anchor. It uses the nearest hit to pull the camera inward along its current
view line.

This is not the host's terrain-height test. The native path calls the engine's
bound scene ray-query interface, with a camera-footprint set of probes. Its
default probe set is five rays: the center line and four corners. A second
mode uses nine rays: the center plus eight perimeter rays spaced at 45°.

## Settings and compiled defaults

`KG3DEngineX64.dll` loader `0x1804c1660` reads the engine `[Camera]` settings.
The setting object is the nested block at `KG3DTrackCamera + 0x298`; the
loader's `rdi` points at that block. Its field `+0x10` is
`bObstructdAvert`. The loader copies that value to the parent track-camera
field `+0x204`, and the frame-update path checks `+0x204` before calling the
obstruction routine at `0x1804c1b40`.

The track-camera constructor initializes these defaults before an ini can
override them:

| `[Camera]` key | Compiled default | Evidence / notes |
|---|---:|---|
| `bObstructdAvert` | **1** | Enables the obstruction call path. |
| `nChaseType` | 2 | Nested config field `+0x18`. |
| `fChaseRate` | π (3.1415927) | Field `+0x1c`. |
| `fMaxDistance` / `fMinDistance` | 4000 / 0 u | Fields `+0x20/+0x24`. |
| `fMaxAngelVel` / `fMinAngelVel` | π/2 / −0.8726646 rad | Fields `+0x28/+0x2c`; the ini key uses the spelling `Angel`. |
| `fAngelRateHor` / `fAngelRateVel` | 0.0062831854 / 0.0062831854 | Fields `+0x30/+0x34`. |
| `fDisZoomRate` | 50 | Field `+0x38`. |
| `fFlexCoefficient` | 1.5 | Field `+0x08`. |
| `fDampCoefficient` | 2·√2 ≈ 2.828427 | Field `+0x0c`, computed in the constructor. |
| `bUseFlexibilitySys` | 1 | Field `+0x14`; copied to parent `+0x208`, separate from obstruction. |
| `fFlexRate` | 500 | Field `+0x3c`. |

`fDistance`, angles, lock state, and FOV are initialized from/query the current
camera state in the loader rather than all being literal constructor values.
The loader seeds the FOV fallback from a value of 0.785398 rad (45°) before
querying the active camera.

No current `[Camera]` ini with these keys was found in the scanned local
client, MovieEditor, or `_HttpFileForDebug_` config trees. These are therefore
the verified constructor defaults, not proof that a streamed runtime ini does
not override them.

## Per-frame obstruction rule

### Gate and inputs

The `KG3DTrackCamera` update path tests parent field `+0x204` (loaded from
`bObstructdAvert`). If it is zero, it skips the obstruction call. If enabled,
it passes the current candidate camera position as both input and output,
and passes the current look-at/anchor position separately. The scene-query
object is the camera's bound scene at `+0x118`.

### Probe sets

The helper at `0x1804c1b40` selects its probe set from a separate camera field,
`+0x15c`:

- **Default (`+0x15c == 0`): 5 rays.** One center ray plus four corner rays.
  The corners are formed from the camera's two projected basis offsets in the
  `+0x12c..+0x134` and `+0x144..+0x14c` fields. The base-camera constructor
zeros `+0x15c`, so this is the compiled default mode.
- **Alternate (`+0x15c != 0`): 9 rays.** One center ray plus eight perimeter
  rays. The perimeter uses `θ = 0, π/4, π/2, …, 7π/4`, generated by an
  eight-step loop; the same camera basis/projection data shapes the endpoints.

The `+0x15c` setter exists at `0x180448020`, but its higher-level meaning or
configuration source has not been identified. It is not the
`bObstructdAvert` flag.

### Ray query and position correction

For each probe pair, the engine uses the anchor-side point as ray origin and
points the ray toward its corresponding desired camera-side point. It
normalizes that segment direction and uses the segment length as the maximum
query distance. The query option passed by this path is `1`; the engine query
wrapper (`0x180446920`) converts it to internal filter mask `0x301` and
attaches the static **`FilterCamera`** intersection filter (RTTI
`.?AUFilterCamera@?A0x573b9fc1@@`, object at `0x180946678`); the selection
path attaches a sibling **`FilterLogic`** filter instead. The dispatcher
(`0x18032ea40`) runs the mask's geometry backends and keeps the nearest
positive hit. Mask bit 9 reaches
`KG3DSceneSceneEditor::RayIntersectRenderEntity` (`0x1804a19f0`, which
iterates the scene entity list at `+0x7000`); mask bit 8 reaches other scene
intersection helpers (`0x18032ed10` → `0x18032ef50`/`0x18032f0b0` →
`0x18008af20`/`0x18038b6e0`/`0x1803aa8b0`). The engine string table names the
related functor family `RayIntersectionTerrain`, `RayIntersectionVertical`
and `RayIntersectionEntity` (`KG3DIntersectionFilter` parameter). The exact
split of the `0x301` bits between those categories is not recovered, but the
filter object identifies the camera path unambiguously.

Let `C` be the desired camera point, `A` the look-at anchor, and `hᵢ` a hit
distance measured from anchor-side probe `Aᵢ` toward camera-side probe `Cᵢ`.
When any probe hits, the helper takes the smallest hit distance and writes:

```text
u = normalize(C - A)
C' = A + u * max(0.001, min(hᵢ))
```

The 5/9 probes provide the camera-footprint clearance; the final camera point
is moved along the center view line. With no hit, the candidate camera point
is returned unchanged. The helper uses a 0.001-u lower bound for the final
distance.

The caller then applies a fixed wall clearance of its own (`0x1804c127d`): the
final camera position becomes

```text
C'' = C' + normalize(A - C') * 18.0
```

i.e. the camera sits **18 u (0.18 m) short of the hit point**, on the anchor
side. The caller also keeps a per-camera hysteresis state (`+0x1cc`): while
not currently obstructed a shortening hit only applies if it is within a 50-u
threshold of the camera's reference point; while already obstructed the
threshold is 100 u. This prevents flicker when the camera hovers exactly at
the obstruction boundary. On a shortening hit the update sets the obstruction
state (`+0x1dc |= 0x0C`, `+0x1c4 = 1`, `+0x1cc = 1`); when the helper returns
an unchanged candidate the same path clears it (`+0x1dc &= ~4`,
`+0x1cc = 0`).

The ray length is derived from the current candidate camera/anchor sample
pair. `NearByWallDistance=800` is **not** the max length supplied to these
engine rays and is not the 18-u clearance.

### Return dynamics (flex state)

The same update also runs a damped state integrator, enabled when
`bUseFlexibilitySys` (`+0x208`) is set and the camera state is initialized
(`+0x1c4 != 0`). Recovered from `0x1804c0e84..0x1804c10f7`:

```text
E  = desired - reference                 ; fields +0x170 / +0x17c
S += ( -fFlex * E - fDamp * S ) * dt     ; state S at +0x1b8..+0x1c0
X   = desired + S * dt
accept X when angle(reference->X, reference->desired) <= 0.05 rad,
otherwise fall back to the reference position
```

with `fFlex = +0x1fc` (default 1.5), `fDamp = +0x200` (default 2.828) and
`dt` in seconds (engine timer delta / 1000). When flexibility is off the
camera takes the reference position directly (`0x1804c10c0`). This is what
eases the camera back out once an obstruction clears; the only part not
pinned to the instruction level is which of the `+0x170`/`+0x17c` fields is
the desired vs. the reference position (their roles are inferred from the
surrounding reads/writes).

## What happens when a wall is approached

As the desired camera point reaches a configuration where one of the tested
segments intersects scene collision, the nearest hit distance pulls the
camera toward the anchor until it is at the reported obstruction point. The
test repeats during camera updates, so the camera remains pulled in while the
scene query continues to report a hit. When the rays clear, the helper stops
shortening the candidate and the normal chase-camera update resumes its
desired placement.

The helper itself does not smooth the obstruction; the 18-u clearance and the
50/100-u hysteresis live in the caller. The enclosing track-camera update also
maintains chase/flex state (`fChaseRate`, `fFlexCoefficient`,
`fDampCoefficient`, and `bUseFlexibilitySys`), so the exact return-time curve
once the rays clear is governed by that (spring/flex) update path. That
return timing has not yet been isolated.

## `bObscatleCamera` — the per-mesh obstruction property

The camera ray path is gated per mesh. `KG3DMesh` owns a `[Display]` property
block at `+0x194` (five bools: `bAutoProduceObstacle` `+0x194`,
**`bObscatleCamera` `+0x198`**, `bSelectable` `+0x19c`, `bHeightTest`
`+0x1a0`, `bOccluder` `+0x1a4`). The `KG3DMesh` constructor (`0x180250430`)
sets all five to **1**, so meshes obstruct the camera by default.

Two paths read it:

- The scene-ray filter used by the chase camera (`FilterCamera`) calls the
  display-block getter (`0x180254080`, which returns `mesh+0x194`) and reads
  `+4` — the `bObscatleCamera` bool — as its per-object test.
- The model near-ray path (`KG3DModel::GetCameraNearRayIntersect`, `0x1801ef000`)
  is reached only for models whose mesh has `bObscatleCamera != 0`: both
  callers (`0x18016d320` and `0x180545500`) call the same display-block getter
  and skip the model when the value is zero.

Content uses the key both ways. Extracted mesh-property inis show
`bObscatleCamera=1` on walls, stones, rubble, cactus and NPC/player body
meshes, while selected meshes ship `bObscatleCamera=0` (small wood/plant
pieces, altar/tomb decorations and similar) so the camera does not collide
with them.

Inside `GetCameraNearRayIntersect`, the per-element flags dword at `+0xb0` is
tested against `0x20000`; the elements come from the object at `model+0x298`
(indexed via `0x180242010`: count `+0x1c`, array `+0xb8`, stride `0x438`).
`KG3DModel::IsRayIntersectBoneBox` then performs the near-ray test against the
model's bone boxes. So `bObscatleCamera` (mesh-level) and the `0x20000` flag
(part/material-level) are two layers of the same "this geometry can push the
camera" property.

## Comparison with the current host/client camera

The inspected host/client camera code still performs a terrain-only march:

- `reborn-merge/client/RebornClient.cs` (current worktree version) places the
  camera using tracked yaw/pitch and per-axis camera-offset smoothing with a
  60 ms `SmoothTime`, then samples terrain at 14 points from `i=2..14`.
  It uses a 20-u clearance margin, pulls inward by `max(150, t·rayLength−40)`
  on a terrain hit, and clamps the result above terrain +30 u.
- `reborn-camera/engine_host_spike/MapSpike.cs` uses the same 14-point,
  terrain-only check. Its hit response currently sets `camY` to the anchor
  height (`vy` is zero) before the final terrain clamp.
- The checked `FoliageCollision` path is for character/support collision;
  no general camera segment ray/sweep was found in the host code.

Thus the host code cannot reproduce native wall/structure hits using its
heightfield sampler alone, and it does not test the mesh-level
`bObscatleCamera` gate. `NearByWallDistance=800` is a real value in the
`JX3RepresentX64.dll` `CommonNumber` struct (embedded at `RL+0x24c14`, field
`+0x104`, i.e. `RL+0x24d18`), loaded from `number.krl.txt`. No reader of that
field was found in the represent camera-controller region, so its consumer
remains unidentified; it is not the native engine ray length, not the 18-u
clearance and not a confirmed trigger rule.

The current `reborn-merge/client/RebornClient.cs` has an existing uncommitted
worktree diff from the other camera work. It was read for comparison and left
untouched by this research.

## Remaining unknowns

- The exact split of the `0x301` mask between the entity, scene-block/terrain
  and other backends, and which map meshes actually have ray-query data.
- The precise contract of the `FilterCamera` slots 1/2 (`0x1804465c0`,
  `0x180446580`: entity type `0x3f` plus `[vt+0xad8]` test) and whether
  gameplay ever toggles `bObscatleCamera` at runtime.
- What sets the alternate `+0x15c` 9-ray mode (setter is camera vtable slot 25
  at `0x180448020`; no direct caller found in the engine).
- How streamed `[Camera]` settings override the constructor defaults in the
  current live client.
- Whether repeated host `SetCameraPos` calls bypass, trigger, or race the
  native track-camera obstruction update.
- Live confirmation of the contact margin and the flex return curve (the
  constants and update law are recovered; only the live feel is unverified).
- `NearByWallDistance` (`CommonNumber+0x104`): loaded but no reader was found
  in `JX3RepresentX64` in this build; likely legacy/unused, not a wall rule.
