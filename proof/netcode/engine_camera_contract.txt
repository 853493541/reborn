Engine camera API contract - recovered 2026-09-27 (Phase 1 of the
engine-faithful camera plan)

Source: MovieEngineCLR.dll (C++/CLI), method KGSceneCLR::SetCameraPos
RVA 0x2728AC (file offset 0x271CAC), IL decoded with dncil. The IL is the
contract the host engine already accepts (SetCameraPos X/Z work today).

Contract (all virtual calls go through the object's first qword = vtable):

  scene = this.m_pScene                       (field token 0x04000FF8)
  camera = scene->vt[+0x50](scene)            (returns the camera object)

  // position read/write on the camera object
  camera->vt[+0x48](camera, &float3 outPos)   // get position (fills 12 bytes)
  camera->vt[+0x50](camera, &float3 pos, 0)   // set position

  // look-at target read/write on the camera object
  camera->vt[+0x60](camera, &float3 outTarget) // get target
  camera->vt[+0x58](camera, &float3 target, 0) // set target (look-at)

  // Y clamp source: the scene's own surface query
  scene->vt[+0x70](scene, &outPos, &float outClampedY, ?)
     ; SetCameraPos IL then does:  if (outClampedY > pos.y) pos.y = outClampedY;
     ; bKeepY=true skips that by using the current position Y instead of fY

  // managed SetCameraPos moves the target by the same delta as the position,
  // which is why the engine view keeps its direction when the pull crosses
  // the anchor (the target translation preserves the old look direction).

  ...

BLOCKED (what did not work, with evidence):
  - Get3DScene2 scene (EngineRay._scene, ray backends work) called at vt+0x50
    with (void*) signature returns 0 -> not the same object/class as m_pScene.
  - The managed KGSceneCLR wrapper address (via __makeref and via weak
    GCHandle deref, both gave the same pointer) scanned over 0x400 bytes
    exposes no field whose target has an engine-code vtable -> the native
    m_pScene is not stored as a plain inline pointer reachable that way
    (C++/CLI layout/GC indirection).
  - The object scanner's "Camera" object (vtable = engine base + 0x21EF6E0,
    class KG3D_Camera) has vt+0x50 = base+0x7B5CA0 and vt+0x58 = base+0x7B5CE0,
    but disassembly at those addresses is mid-function code (no prologue);
    calling them executes garbage/int3 -> engine AV. KG3D_Camera is NOT the
    camera class whose +0x50/+0x58 are the position/look-at setters.

UPDATE 2026-09-27 (same session, after the blocked routes):
  - Prologue-guarded calls were added (int3 padding or common prologue) so a
    wrong vtable entry is rejected instead of AVing: the client never crashed
    with the guard on.
  - RC_CamBind with the relaxed contract still binds wrong objects: the
    latest bind (obj 0x12A1B2400, posOff 0xE40) has vt[+0x48] == vt[+0x58]
    == vt[+0x60] (one generic function), and setting through it has no effect
    on GetCameraPos (read-back fallback fires). None of the root-scanned
    objects is the camera the managed IL uses.
  - The client path is default-OFF (`RC_CAM_ENGINESET=1` to probe), verified
    with a read-back: a native set that does not move the engine camera falls
    back to the managed call, so the probe can never break placement.
  - Conclusion: the managed camera object cannot be reached from outside the
    managed method with the current tools; the hook (or a C++/CLI helper) is
    required to finish Phase 2.
