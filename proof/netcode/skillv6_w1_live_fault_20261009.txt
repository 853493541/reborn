## Engine region — the old "0xE2E842 memcpy caller" attribution is WRONG

## Chain function decoded — `fn 0xE2DA70` = keyframe-curve interpolation
`0x180E2DA70` disasm: `mov rsi,rdx; cvttss2si edi, xmm6(=time); comiss xmm6,0; lea eax,[rdi-1];
cmovb edi,eax` (if time<0 -> edi--), then a **red-black keyframe-tree search** (`cmp byte [node+0x19],0`
colour walk by `[node+0x1c]` key), ending in a lerp (`subss/divss/mulss/addss`). So this is the engine's
**animation-curve evaluator** (time -> interpolated value). A **negative time/frame** makes the index
go negative (`edi--`, e.g. -6); that negative flows into the downstream allocation whose size becomes
`0xFFFFFFFA`. This matches "bad anim/bone id the host model lacks" (a negative time/frame index).

## fn 0xE2E690 indirect calls resolved (no direct jemalloc)
All `call qword [rip+..]` in fn `0xE2E690` resolve to: `EnterCriticalSection` (@0xE2E83C),
`GetCurrentThreadId` (@0xE2E842), `LeaveCriticalSection` (@0xE2E86F), plus one repeated slot
(`0x1C14D50`, a helper). **No direct jemalloc/memcpy call** — so the -6 alloc is invoked from a
deeper frame (not captured as a clean engine return address in the 128-qword scan).

## Code-only stack (executable entries) confirms: no extra frame
Filtering the 128-qword stack to **executable** addresses (per-module PE `.text` ranges) yields the
SAME chain (`ntdll+.. -> jemalloc+.. -> engine 0xE2E842 -> 0xE2DADA -> 0xE2D706 -> 0x10D0A6 ->
0xE2768F`) — i.e. the immediate jemalloc caller is **not** a separate frame on this stack (the fault
thread's `rsp` is a jemalloc/ntdll scratch stack; `rbp` is not a frame pointer). So the exact engine
instruction that calls the bad `jemalloc(size=-6)` cannot be read from this stack alone.

## Lesson (recorded)
An exec BP on a HOT function (`jemalloc+0x11001`) fires every allocation -> per-hit single-step ->
the target **flashes/stalls** (user aborted). Never exec-BP a hot function; use the AV catch (above)
or a cold site. `multi_trace.py` now warns about this and has `--filter` (log only matching hits).

## ROOT FUNCTION — `KG3D_TimeLine<float>::CreateCache` (frame #03)
Frame #03's function is `KG3D_TimeLine<float>::CreateCache` (assert string @0x18225BD68). Body:
```
0xE2E79D movsxd rdi, ebx        ; rdi = COUNT (signed)
0xE2E7AF call  0x18013bba0      ; allocate COUNT elements (rdx=rdi)
0xE2E7EA lea r8, [rdi*4]        ; size = COUNT*4
0xE2E7F7 call  0x181a3bc15      ; memset(dst, 0, COUNT*4)
loop: call 0x180E2DA70 per frame (curve eval)
```
So the crash is `CreateCache` with a **negative COUNT** (`ebx = 0xFFFFFFFA = -6`): the allocate/memset
(and the down-chain `memmove`) get size `-6`. This matches the earlier curve-eval "negative
frame/time" finding — a **missing/invalid animation timeline** makes the computed frame count
negative. The caller chain goes up through the animation-tag pipeline
(`KG3D_AnimationTagX64.dll`) and `KG3D_CreateSFXFromFile` (0xBE4000).

**COUNT formula (decisive):** right before the alloc,
```
mov ebx, r12d      ; r12d = MAX keyframe key (from the red-black keyframe tree)
sub ebx, r15d      ; r15d = MIN keyframe key
add ebx, 1         ; COUNT = maxKey - minKey + 1
```
`ebx = -6` ⇒ `maxKey - minKey = -7`. Note: `r15d`/`r12d` start at **0** and only take node keys
(`cmovl min`, `cmovg max`), so `min <= 0 <= max` and `COUNT >= 1` **by construction** for any
well-formed tree. A negative COUNT is therefore only possible if the traversal reads **corrupt node
keys** — i.e. the `KG3D_TimeLine` object's keyframe map/tree (at `[timeline+8]`) is **corrupt or
uninitialized** (bad node pointers -> garbage keys). So the 39 AV tanis drive `CreateCache` on a
**corrupt/uninitialised timeline** — the actual defect (the animation timeline wasn't loaded/valid).

- the **last** BP-hit (the presumed faulting call, `this=0x11104e9a8`) has a **valid** keyframe tree

So the `-6` does **not** come from an inverted/corrupt min/max of that timeline. The "corrupt
keyframe tree" inference is likely WRONG; the `-6` is produced elsewhere in CreateCache
(the allocate `call 0x18013bba0(rcx=0, rdx=COUNT)`, the `memset(COUNT*4)`, or the per-frame
curve-eval `call 0x180E2DA70`) — or a different `KG3D_TimeLine<T>::CreateCache` instantiation.

## IAT correction (resolved from the dump) — 0xE2E83C is an ALLOCATOR, not EnterCriticalSection
Reading the loaded IAT slots from the dump:
- `call @0xE2E83C` -> `ntdll.dll+0x127F0`  = an **allocator** (`RtlAllocateHeap`), NOT
  `EnterCriticalSection` (my earlier static-ILT name lookup was WRONG).
- `call @0xE2E842` -> `kernel32.dll+0x18620` (`HeapAlloc`-class)
- `call @0xE2E826` -> `kernel32.dll+0x22E70` (`HeapFree`-class)
So `global+0x2D3EEE8` is a **heap handle**, and the `-6` is the **size** passed to the
`RtlAllocateHeap` at `0xE2E83C` (size likely in `r8`, carried/clobbered across the curve-eval loop).
